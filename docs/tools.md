# Model tools

Every tool the chat model can call, what runs where, and the limits that keep them safe for anonymous visitors. Read this before adding or changing a tool in `src/routes/api/chat/+server.ts`, or `src/lib/server/{github-repo,calendar,training,python-sandbox}.ts`.


The LLM can invoke these client-visible functions:

| Function | Effect |
|---|---|
| `minimize_chat` | Minimizes the chat widget |
| `route_to_page` | Navigates the browser to a site page via SvelteKit's `goto()`. Meant as an extra after a text answer, not a replacement — the client keeps any text the model streamed before the call, and the visitor's current page is left out of the allowed routes |
| `reset_conversation` | Clears the conversation and its saved copy (`resetChat`). Only for a clear request ("start over"); typing `clear`, `/clear`, `reset`, `start over` or `new chat` does the same instantly on the client with no model call |

All valid route destinations are defined in `src/lib/types.ts` as the `SupportedRoutes` enum. **When adding new pages to the site, add the route to `SupportedRoutes` so HuntBot can navigate to it.**

Beyond the two client-visible actions above, the model also has server-executed tools it can call mid-turn (not surfaced in the UI as actions): `search_knowledge_base` (additional Qdrant lookups) and four GitHub self-awareness tools backed by `src/lib/server/github-repo.ts` — `read_github_file` reads a file live from the `hunterbryant/huntbot` repo via unauthenticated `raw.githubusercontent.com` (defaulting to `CLAUDE.md`); `get_recent_commits` fetches the latest commits (message/author/date); `get_repo_info` fetches repo age/size/stars/language breakdown; and `search_repo_code` searches file paths/contents for a keyword to find the right file before reading it. The commit/info/search tools go through GitHub's unauthenticated REST API (`api.github.com`, ~60 req/hr limit; code search is a tighter ~10 req/min). Together they let HuntBot answer technical questions about its own architecture and recent changes without a separate embedding/re-indexing step. Each tool's `execute` reports a specific `data-status` label (e.g. "Searching my code…", "Reading CLAUDE.md…") so the chat loading indicator reflects exactly what it's doing instead of a generic "thinking" phrase.

A fifth server-executed tool, `get_calendar_events` (`src/lib/server/calendar.ts`), answers "what was Hunter up to on [date]" style questions by querying Hunter's Google Calendar live via OAuth2 (refresh-token flow, no user login involved — see `GOOGLE_CALENDAR_*` env vars). It intentionally returns only event titles and times, never attendees, locations, or descriptions, since results are exposed to anonymous site visitors. Requires a one-time OAuth consent flow to mint `GOOGLE_CALENDAR_REFRESH_TOKEN`; without it configured, the tool degrades gracefully ("Calendar is not connected.") rather than erroring.

Two more server-executed tools answer questions about Hunter's training, from intervals.icu (`src/lib/server/training.ts`, `INTERVALS_*` env vars). `get_training_totals` covers "how much did he bike this year": totals by sport (count, miles, moving hours, feet climbed) from intervals.icu's weekly buckets, plus current fitness (CTL). `analyze_training_data` is for questions that need computing (biggest week, year-over-year, longest ride, heart rate, morning vs evening, where he rides). The model writes a stdlib-only Python script, and `runPython` (`src/lib/server/python-sandbox.ts`) runs it in a throwaway Vercel Sandbox (`vercel/sandbox/python:3.14`, 1 vCPU, stopped right after) with `weekly.csv`, `fitness.csv`, `activities.csv` and `wellness.csv` (every daily wellness field intervals.icu has: sleep score and duration, HRV, resting HR, readiness, steps, weight, …) preloaded. Only stdout/stderr come back, capped at 4k chars, with a 30s command timeout.

- **Live API access from the sandbox.** For anything not preloaded (power curves, gear, planned workouts, intervals, best efforts, streams, the profile), the script can call the intervals.icu API itself. `intervalsNetworkPolicy()` in `training.ts` sets the sandbox's network policy so only intervals.icu is reachable, and only `GET /api/v1/athlete/{INTERVALS_ATHLETE_ID}/…`, `GET /api/v1/docs` (the OpenAPI spec, for looking up endpoints) and `GET /api/v1/activity/{id}/…` for the activity IDs in the loaded date range (up to 300, taken from his own activity list). Activity IDs are scoped because an ID alone doesn't prove whose it is: athletes he follows or who shared with him have activities his key can open, so a bare `/activity/{anyId}` rule would expose them. Vercel's sandbox proxy adds the `Authorization` header, so the API key never enters the sandbox. Everything else gets a 403 from the proxy: writes and deletes, other athletes, `/chats`, `/athlete-summary` (it also returns the athletes Hunter follows; `weekly.csv` already has his own) and `/shared-with` lists, and any path containing `..`, `//`, `;` or a `%` (intervals.icu decodes paths, so `/%63hats` would otherwise reach `/chats`; its paths are case-sensitive, so case variants just 404). Keep the policy's regexes to plain syntax: Vercel validates them with a JavaScript-compatible parser even though matching is RE2, and an inline `(?i)` flag made every sandbox creation fail with "is not a valid regular expression". If the API ever refuses the policy again, `runPython` reruns with `deny-all` (logged as `network_fallback`), so the preloaded files still answer.
- **Exact locations and tracks reach the model.** Hunter chose that. `include_location` puts each ride's start, end and center (to about 10 m) in `activities.csv`, and a script can also read a whole GPS track from `/activity/{id}/streams.json` or `/map` and print it. Nothing strips them out, so anything the script prints is visible to visitors; the prompt only asks for place names rather than raw coordinates. Wellness comments (free text) are in `wellness.csv` too.
- **Turn budget.** A turn that calls `analyze_training_data` gets up to `MAX_ANALYSIS_STEPS` (6) model steps instead of `MAX_STEPS` (3), so the model can fix a failing script or run a follow-up query before answering. The chat route sets `maxDuration: 300`, and `ANALYSIS_DEADLINE_MS` (200s into the request) stops new analysis runs and the step loop, so a slow turn ends with an answer instead of the function being killed mid-stream. Lane `maxOutputTokens` caps (2,000 quick/standard, 3,000 deep) are sized so a step can hold a script plus reasoning.

- **Strava-synced activities are invisible per activity.** intervals.icu's API returns an empty stub for anything that came in through Strava (Strava's API terms). Weekly totals still count them, so totals are complete, but `activities.csv` only has activities recorded straight to intervals.icu (e.g. a Karoo or Garmin connection), and the tool result says how many are hidden. To fill them in, connect the device to intervals.icu directly and use "Download old data" on its Connections page.
- **Fields:** per activity, the model can see the date and start time, name, sport, distance, moving time, elevation, average power, training load, average and max heart rate, weight, and device; weekly rows add fitness/fatigue/form and weight. The prompt says to share these as plain facts without reading anything medical into them.
- **Location is opt-in.** The activity list has no coordinates, so `include_location: true` downloads each activity's GPS track from `/activity/{id}/map` (most recent 50 outdoor ones, 10 at a time) and keeps only the start point, end point and bounding-box center, to 4 decimal places (about 10 m). Only those points are cached (per warm instance, for its lifetime), and `include_location` itself never passes a track to the model, though a script can fetch one (see "Exact locations and tracks reach the model" above). Hunter chose exact locations knowing that start points usually reveal home; the prompt asks for place names rather than raw coordinates.
- **Auth:** the sandbox authenticates with the Vercel function's OIDC token (on by default for the project; check Settings → Security → Secure backend access with OIDC federation if runs fail with an auth error). Locally it needs `VERCEL_OIDC_TOKEN` from `vercel env pull`; without it the tool is skipped rather than starting the SDK's interactive login.
- **Observability.** Each training tool call logs one `[HuntBot training]` line (see [observability.md](observability.md)) and the turn's `chat_message` event gets `training_*` / `analysis_*` properties, so a failing script, a sandbox problem, a hidden-Strava gap or a missing env var shows up without reading the model's reply. `server_tool_args` already carries the script the model wrote. `analysis_fetch` / `analysis_sandbox` (summed over the turn's runs) join the `[HuntBot timing]` line and `timings_ms`, and `tool_<name>` there is now the total across a turn's calls rather than the last call. The proxy's 403s for blocked sandbox requests aren't visible from our side.
- Weekly buckets run Monday–Sunday, so a range's edges can include a few days outside it; the tool output says which whole weeks it covered.

## Knowledge tools: Notion, job postings, HuntBot's own docs

Server-executed tools that read sources outside the Qdrant index. Each logs one `[HuntBot tools]` line and adds properties to `chat_message` (see [observability.md](observability.md)).

- **`query_notion`** (`src/lib/server/notion.ts`) reads everything the Notion integration can see, live, as a small agent loop rather than a text search (text search can't answer "what did he do the last week of Sept": dates in titles aren't searchable and relevance ranking knows nothing about ranges). One tool, four `action`s the model chains across steps: `search` (words → pages, with ids; reads the top 3 bodies), `describe` (no database: lists the shared databases with sample titles so a vague name like "Agenda" can be told apart; ambiguous names return the candidates instead of picking one; with one: property names, types and select/status options, cached 1h), `query` (typed `filters` on a database: `property` + `op` + `value`, ANDed; `sort_by`, `limit` ≤ 10, `include_content` reads up to 8 matching bodies) `titles_only` (one line per row, up to 100 with a `cursor`, for databases whose dates live in the titles rather than a date property, e.g. "Daily Agenda Sept 24"; an empty filtered query hints at it) and `read` (up to 8 pages by id). `buildFilter` maps the flat ops onto Notion's per-type filters (text, number, date and created/last-edited timestamps, select, status, multi-select, checkbox) and validates against the real schema; a wrong property, operator, date or option comes back as a `bad_request` that lists the valid choices, so the model fixes the call on its next step. People, relation, rollup, formula and files properties can't be filtered. A turn that calls it gets the longer step budget (`MAX_ANALYSIS_STEPS`). Bodies read to depth 2, 2,000 chars per page and 8,000 per call; 10s budget; results cached 5 minutes. Never returns workspace links. Scope is whatever the integration is shared with; control it in Notion's Connections settings. Live results skip the chunk audit's sensitivity filter, so the prompt tells the model to paraphrase and never quote private details about other people. The page-to-text helpers are shared with the embed job (`routes/api/embed/notion-url`), which keeps its 350ms request spacing.
- **`explain_huntbot`** (`src/lib/server/self-docs.ts`) answers "how do you work" from HuntBot's own write-ups: the Building HuntBot post (fetched uncapped; `getSitePageText` cuts pages at 10,000 chars and the post is about 30,000) and the repo's `docs/*.md` and `CLAUDE.md` (read from `main` via `readRepoFile` with `maxChars`). Sections are split at headings (at most 1,500 chars, cut at list-item and sentence boundaries), embedded once per warm instance (30-minute index), and the best four for the question come back, with the post ahead of the docs on ties. Because it reads `docs/` from `main`, keep those files accurate: they are what visitors hear.
- **`match_job_description`** (`src/lib/server/job-match.ts`, `safe-fetch.ts`) takes a pasted posting or a link and returns, for each of up to 8 requirements, evidence from Hunter's public writing (site pages and notes, never iMessage, chunk-audit exclusions respected) or an explicit "no clear evidence". Posting text comes from the Greenhouse, Lever and Ashby APIs for links to those boards (clean text), or from `safeFetchText` for any other page. One `gpt-6-luna` call extracts the requirements; the posting is untrusted and the prompt says so. A requirement scoring below `EVIDENCE_MIN_SCORE` (0.35, uncalibrated: tune it from `jd_gaps`) counts as a gap, and the prompt tells the model to name real gaps and never invent experience.
- **`safeFetchText`** (`src/lib/server/safe-fetch.ts`) is the only way to fetch a URL a visitor typed. https only, no credentials or non-443 ports, the host must resolve to public addresses only (loopback, private, link-local, multicast, carrier-grade NAT, documentation ranges and the IPv6 equivalents are refused, including IPv4-mapped forms), the connection is pinned to the checked address so DNS can't be swapped after the check, redirects are followed by hand (3 max) and re-checked, and time (5s), size (1 MB after decompression) and content type (HTML, text, JSON) are capped. New code that fetches visitor-supplied URLs must use it.
- **`find_open_roles`** is the same lookup for a company the visitor *names* ("I'm at Uber", "we're hiring a maps designer"), so HuntBot finds the role itself instead of asking for a posting. It has only a name (no domain), so slugs come from the name, and because someone asked it waits for the web search (up to 8s) when no job board exists; links from a search are trusted only on a job board or on the company's registrable domain (`careers.uber.com`, not `uber.evil.example`). The prompt forbids describing a company's roles from memory: only roles from the Visitor hints or this tool. Companies without a public job board (Uber, for one) depend entirely on the web search, which needs `OPENAI_API_KEY` and isn't disabled by anything but `COMPANY_ROLES_WEB=0`; check `[HuntBot tools]` `company_roles` lines (`source`, `results`) after deploying. Every visitor-named company can trigger a web search, cached 12h per company.
- **Open-role lookup from the network** (`src/lib/server/company-roles.ts`) feeds the Visitor hints. When the IPinfo lookup says the network is a company (`orgClass === 'org'`), it guesses job-board slugs from the org's domain and name and asks the public Greenhouse, Lever and Ashby APIs in parallel (2.5s each, about 2.8s overall), keeps design roles (not "Design Engineer"), and caches the answer for 12 hours (misses for 1 hour). With no board found it answers "none" at once and runs a web search (`openai.tools.webSearch()` on `gpt-6-luna`) in the background, whose result serves later turns; links it returns are only trusted on the company's own domain or a known job board. Disable the web fallback with `COMPANY_ROLES_WEB=0`. The chat route waits for it only as long as retrieval takes, so it never delays a reply. A guessed company can be wrong (VPNs, coworking, parent companies), which is why the prompt only lets HuntBot ask about a role as a question; see [visitor-context.md](visitor-context.md).
