# Visitor context

The signals each chat turn carries about the visitor, and the rules for using them. Read this before changing `src/lib/visitorContext.ts`, `src/lib/server/visitor-context.ts`, `src/lib/server/ip-org.ts` or the "Visitor hints" prompt rules.


Each chat turn carries a few signals about the visitor so replies can adjust emphasis, length and date math. The model only ever sees short derived labels in a `## Visitor hints (internal)` block inside `## Live details` (so the static prompt prefix stays cacheable); it never sees the IP, user agent or raw URLs, and the context is deliberately kept out of retrieval and the first-turn context cache key.

- **Arrival**: the landing referrer (off-site only; `$referrer` on `$pageview` is overwritten by in-site navigation, so it's kept separately as `landing_referrer`) and a `?via=<slug>` / `?utm_source=` link tag, bucketed into `campaign:<slug>` / `linkedin` / `search` / `social` / `referral:<domain>` / `direct`. Most visits are `direct` (LinkedIn, Slack, iMessage and email strip the referrer), so tag the links Hunter sends with `?via=`. The tag is stripped from the address bar after it's read.
- **Pages read** this visit (last 10, with rough dwell time, current page excluded), **device** (phone vs desktop), **returning** visitor, and the visitor's **timezone** (so "yesterday" uses their date; calendar results stay in Hunter's timezone).
- **Server-derived**: browser language from `Accept-Language` (only when not English), country from `x-vercel-ip-country`, and the **network owner** from an IPinfo Lite lookup (800ms timeout, 1h in-memory cache, runs in parallel with retrieval). The lookup is classified `isp` / `mobile` / `hosting` / `org`; only `org` reaches the prompt, since "Comcast" isn't a company visiting.
- **Never-mention rule**: the static prompt tells the model to use hints only for emphasis, length and date math, never to name the visitor's origin, location, device, language or reading history unprompted, and to answer "what do you know about me?" honestly and generally.
- **The company exception**: when the network is a company and `lookupCompanyRoles` (see [tools.md](tools.md)) found open design roles there, a hint line lists them (title, location, link) and HuntBot asks about it proactively, once per conversation, as a question ("Are you hiring for the Maps designer role at Acme?"). The question comes with tappable answers in the chat (a `data-options` part, see `ask_visitor` in [tools.md](tools.md)): when one role clearly fits Hunter best (`rankRolesForHunter`, cheap title scoring in `company-roles.ts`) it asks about that one ("Yes, that one" / "No, I'm not hiring for that"); otherwise it lists up to three roles plus "No, I'm not hiring for these roles". Two paths: (1) **the opener**: `prefetchRoleOpener` (`MessageStore.svelte.ts`, called by `ChatBox` after 8s on the page) calls `POST /api/chat/role-opener` while the chat is still closed; if it finds roles, the minimized input bar (not the "Ask HuntBot" greeting) shows the response's short `teaser` line ("Spotted an open design role at Acme. Yours?") with the usual per-letter reveal, ahead of hover/scroll suggestions for the first 10s and in place of the idle text after that, and tapping the bar opens the chat. When the chat opens with no conversation, `triggerRoleOpener` posts the opener as the first message, in place of the canned greeting, reusing that lookup (or making the call itself if the chat opened first). The endpoint, which runs the company-identification stack below (waiting up to 2s for the pixel and any first-time referrer) and `lookupCompanyRoles`, and returns a fixed-template message (no LLM, so it can't invent a role) with those options; it is skipped when `VISITOR_CONTEXT=0` or no company is found, once per browser session, and the message sits in the chat history so the model sees that it was asked. (2) **the first-reply fallback**: if the visitor types before the opener lands, the prompt tells HuntBot to end its first substantive reply with the question, unless an earlier assistant message already asked. Never as a greeting or its first words. **Simulating a company**: typing `/simulate Airbnb` in the chat (handled client-side like `clear`, no model call, not advertised) restarts the chat as if the visitor were on that company's network; `/simulate off` goes back to normal. The name is kept in `sessionStorage` and sent as `visitor.simulatedOrg`: the chat route uses it in place of the IPinfo lookup (so the hints block, the roles line and the prompt rule all apply) and the opener endpoint takes it as `simulateOrg`, ignoring GPC since the visitor named the company on purpose. Anyone can use it; because the name picks who gets looked up (an LLM web search), both the opener and the chat route share a per-address rate limit (`lookup-limit.ts`, 8 per 10 minutes per warm instance) and the chat says so when it's hit. It only ever affects that visitor's own chat; names are validated (`simulatedOrg` in `ip-org.ts`), and turns carry `simulated_org: true` on `chat_message` so they can be filtered out. If no roles are found, the chat says so. If they say no or ignore it, it drops it; with no roles listed it must not mention the company at all. The network is only a guess (VPNs, coworking spaces, parent companies), hence the question form. This replaced a blanket ban on naming the company. `replyMentionsOrg` still records, as `visitor_org_mentioned` on `chat_message`, whether a reply named the network the visitor hadn't; it's now a measure of how often the ask happens, not a warning line. Open roles are skipped under GPC (no lookup happens).
- **Global Privacy Control** (`Sec-GPC: 1` or `navigator.globalPrivacyControl`): no IP lookup (neither IPinfo nor ipapi.is), so no network-derived company; the stated, simulated, pixel and referrer company layers still apply (Hunter's choice for this proof of concept; see Company identification below), no `$ip` / `$raw_user_agent` on any event, `$geoip_disable: true`, and only `gpc: true` is recorded instead of the `visitor_*` properties. In-prompt hints (device, timezone, pages, language) still work for the reply itself.
- All client values are re-validated server-side (slug and domain patterns, `Intl` timezone check, known site routes only). Kill switch: `VISITOR_CONTEXT=0`.

## Company identification (`src/lib/server/visitor-company.ts`)

Which company the visitor works at comes from a stack of independent layers, so it no longer depends on the IP alone. `resolveVisitorCompany` runs them for every chat turn (no waiting) and for the chat-open opener (`/api/chat/role-opener`, which waits up to 3s for the pixel), and returns `{ name, domain, source, confidence, agreedWith }`:

| Layer (`source`) | Signal | Base confidence |
|---|---|---|
| `simulated` | `/simulate <Company>` (testing, treated like a network guess in wording) | certain |
| `stated` | the visitor said where they work: `find_open_roles` with `visitor_works_there: true` sends a transient `data-company` part, the client keeps it in `sessionStorage` (`huntbot_stated_company`) and sends it back as `visitor.statedCompany` | certain |
| `pixel` | RB2B identity pixel, see below | high |
| `referrer` | the landing referrer host names an employer, see below | medium |
| `ip_company` | ipapi.is: WHOIS owner of the IP block, only when `company.type` is `business` (`ipapi-is.ts`, `IPAPI_IS_KEY`, free 1,000 a day, 800ms, 1h cache) | medium |
| `ip_asn` | IPinfo Lite ASN owner, only when `orgClass === 'org'` (`ip-org.ts`) | low |

Each candidate's confidence goes up one level when another layer names the same company (normalized name or the same domain label); the most confident wins and layer order breaks ties, so two IP layers that agree beat a lone referrer guess. An ipapi.is VPN / datacenter / proxy / Tor flag silences both IP layers. The result replaces the old IPinfo-only `org` (`companyAsOrg`), so the hints, the role lookup and the opener work as before; the hint line says how the company was found ("they said so" vs "a guess from…", plus "fairly confident" when layers agree), and the opener drops "Quick guess" for a stated company.

- **Pixel (RB2B).** `loadIdentityPixel` (`src/lib/visitorContext.ts`, called from `+layout.svelte` with Hunter's RB2B key, overridable with `PUBLIC_RB2B_KEY` or turned off with `PUBLIC_RB2B_KEY=off`; never in local dev) puts this tab's random token in the URL (`?hb=`) before loading the script, and removes it 20s later. RB2B POSTs each identified page view, with its URL, to `POST /api/visitor-id/rb2b/<RB2B_WEBHOOK_SECRET>` (no HMAC from RB2B, so the secret path is the guard; wrong secret → 404). `parseRb2bRecord` (`rb2b.ts`) keeps only the token, company name and website; person fields (name, email, LinkedIn) are dropped and never stored. Records live 24h in the shared store. The pixel loads for every visitor, GPC included: Hunter's call for this proof of concept.
- **Referrer.** No hand-kept host lists. `companyFromReferrer` (`referrer-company.ts`) never asks about hosts that can't name an employer: no subdomain (`uber.com`, `notion.so`), or a public-hosting suffix from the Public Suffix List's private section (`*.notion.site`, `*.github.io`, `*.vercel.app`; via `tldts`). Any other new host gets one small `gpt-6-luna` call ("is this an employee-only tenant subdomain like acme.atlassian.net?"), and an answer that names the host's own site is rejected (`acme.atlassian.net` → never Atlassian, `eng.uber.com` → never Uber). Results are cached per host for 30 days (memory + shared store).
- **Shared store** (`visitor-id-store.ts`): a separate Qdrant collection `<QDRANT_COLLECTION>_visitor_ids` (1-dim dummy vectors, created on first use), keyed by a hash of kind + key, with occasional cleanup of expired records. It exists because the webhook and the chat turn land on different serverless instances.
- **GPC**: the IP layers are skipped; `stated`, `pixel`, `referrer` and `simulated` still count (and survive into the hints, which otherwise drop the company under GPC). The chat route and the opener apply the same rule.
- **Limits and timing**: a company the visitor names (`stated`, `/simulate`) is rate limited per address by *new* name (`allowCompany`, 8 per 10 minutes; repeating a name is free), as is classifying a first-time referrer host (`allowLookup`); a chat turn waits at most 1.5s for the whole stack (`COMPANY_CAP_MS`), classifies a new referrer host in the background rather than waiting, and every shared-store call is capped at 1.5s. ipapi.is failures are cached 30s (successes 1h), referrer failures 5 minutes. The `?hb=` pixel token is stripped from `$current_url` / `$referrer` before any PostHog event.
- Each resolution logs one `[HuntBot visitor-id]` line (see [observability.md](observability.md)).
