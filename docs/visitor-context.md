# Visitor context

The signals each chat turn carries about the visitor, and the rules for using them. Read this before changing `src/lib/visitorContext.ts`, `src/lib/server/visitor-context.ts`, `src/lib/server/ip-org.ts` or the "Visitor hints" prompt rules.


Each chat turn carries a few signals about the visitor so replies can adjust emphasis, length and date math. The model only ever sees short derived labels in a `## Visitor hints (internal)` block inside `## Live details` (so the static prompt prefix stays cacheable); it never sees the IP, user agent or raw URLs, and the context is deliberately kept out of retrieval and the first-turn context cache key.

- **Arrival**: the landing referrer (off-site only; `$referrer` on `$pageview` is overwritten by in-site navigation, so it's kept separately as `landing_referrer`) and a `?via=<slug>` / `?utm_source=` link tag, bucketed into `campaign:<slug>` / `linkedin` / `search` / `social` / `referral:<domain>` / `direct`. Most visits are `direct` (LinkedIn, Slack, iMessage and email strip the referrer), so tag the links Hunter sends with `?via=`. The tag is stripped from the address bar after it's read.
- **Pages read** this visit (last 10, with rough dwell time, current page excluded), **device** (phone vs desktop), **returning** visitor, and the visitor's **timezone** (so "yesterday" uses their date; calendar results stay in Hunter's timezone).
- **Server-derived**: browser language from `Accept-Language` (only when not English), country from `x-vercel-ip-country`, and the **network owner** from an IPinfo Lite lookup (800ms timeout, 1h in-memory cache, runs in parallel with retrieval). The lookup is classified `isp` / `mobile` / `hosting` / `org`; only `org` reaches the prompt, since "Comcast" isn't a company visiting.
- **Never-mention rule**: the static prompt tells the model to use hints only for emphasis, length and date math, never to name the visitor's origin, location, device, language or reading history unprompted, and to answer "what do you know about me?" honestly and generally.
- **The company exception**: when the network is a company and `lookupCompanyRoles` (see [tools.md](tools.md)) found open design roles there, a hint line lists them (title, location, link) and HuntBot asks about it proactively, once per conversation, as a question ("Are you hiring for the Maps designer role at Acme?"). The question comes with tappable answers in the chat (a `data-options` part, see `ask_visitor` in [tools.md](tools.md)): when one role clearly fits Hunter best (`rankRolesForHunter`, cheap title scoring in `company-roles.ts`) it asks about that one ("Yes, that one" / "No, I'm not hiring for that"); otherwise it lists up to three roles plus "No, I'm not hiring for these roles". Two paths: (1) **the opener**: the first time the chat opens with no conversation, `triggerRoleOpener` (`MessageStore.svelte.ts`) calls `POST /api/chat/role-opener`, which does the same IP lookup and `lookupCompanyRoles` and returns a fixed-template message (no LLM, so it can't invent a role) with those options; it is skipped under GPC or `VISITOR_CONTEXT=0`, once per browser session, and the message sits in the chat history so the model sees that it was asked. (2) **the first-reply fallback**: if the visitor types before the opener lands, the prompt tells HuntBot to end its first substantive reply with the question, unless an earlier assistant message already asked. Never as a greeting or its first words. **Simulating a company**: typing `/simulate Airbnb` in the chat (handled client-side like `clear`, no model call, not advertised) restarts the chat as if the visitor were on that company's network; `/simulate off` goes back to normal. The name is kept in `sessionStorage` and sent as `visitor.simulatedOrg`: the chat route uses it in place of the IPinfo lookup (so the hints block, the roles line and the prompt rule all apply) and the opener endpoint takes it as `simulateOrg`, ignoring GPC since the visitor named the company on purpose. Anyone can use it; because the name picks who gets looked up (an LLM web search), both the opener and the chat route share a per-address rate limit (`lookup-limit.ts`, 8 per 10 minutes per warm instance) and the chat says so when it's hit. It only ever affects that visitor's own chat; names are validated (`simulatedOrg` in `ip-org.ts`), and turns carry `simulated_org: true` on `chat_message` so they can be filtered out. If no roles are found, the chat says so. If they say no or ignore it, it drops it; with no roles listed it must not mention the company at all. The network is only a guess (VPNs, coworking spaces, parent companies), hence the question form. This replaced a blanket ban on naming the company. `replyMentionsOrg` still records, as `visitor_org_mentioned` on `chat_message`, whether a reply named the network the visitor hadn't; it's now a measure of how often the ask happens, not a warning line. Open roles are skipped under GPC (no lookup happens).
- **Global Privacy Control** (`Sec-GPC: 1` or `navigator.globalPrivacyControl`): no IP lookup, no `$ip` / `$raw_user_agent` on any event, `$geoip_disable: true`, and only `gpc: true` is recorded instead of the `visitor_*` properties. In-prompt hints (device, timezone, pages, language) still work for the reply itself.
- All client values are re-validated server-side (slug and domain patterns, `Intl` timezone check, known site routes only). Kill switch: `VISITOR_CONTEXT=0`.
